# 遠端型錄合約

本文件記錄 Spec Kit 以遠端／型錄為後端的原語在保持行為不變下的合約：

- 擴充功能
- 預設集
- 整合
- 工作流程
- 工作流程步驟類型
- 套件組

它定義未來共用型錄層的邊界。它不要求目前的實作移入該層，也不改變任何既有的信任、安裝、網路、快取或使用者介面行為。

[共用命令應用架構](shared.md) 仍是具主導性的應用層設計。未來的型錄層是位於 CLI 與 MCP 配接器之下的聚焦領域服務，而不是中央命令分派器或配接器擁有的抽象。

## 範圍之外

「型錄」一詞的另外兩種用法刻意分開：

- `ArtifactCatalog` 解析本機已安裝的構件貢獻與組合堆疊。它不是遠端來源型錄。
- `specify_cli.mcp_server.catalog` 是 MCP 命令公開方式的明確清單。它描述工具與配接器中繼資料，而不是可下載的內容。

兩者都不屬於此處所述的共用遠端型錄層。

## 目前的來源模型

各實作使用兩種來源堆疊模型。

### 取代層型錄

擴充功能、預設集、整合、工作流程與工作流程步驟類型，恰好解析一個來源層：

1. 環境覆寫可取代每個已設定／預設的來源。
2. 當專案設定提供作用中的堆疊時，專案設定取代使用者與內建層。
3. 當使用者設定提供作用中的堆疊時，使用者設定取代內建層。
4. 否則使用內建的官方與社群來源。

在所選層內，數字較小的 `priority` 表示較高的優先順序。相同優先順序保留來源檔案順序，因為目前的載入器使用穩定排序。

內建官方來源允許安裝。內建社群來源僅供探索。目前環境覆寫已啟用安裝。已設定的來源在省略 `install_allowed` 時，預設僅供探索。

環境值的正規化並不一致。擴充功能與預設集先測試原始變數是否存在，再將其去除空白，因此只含空白的值會選擇覆寫路徑並在 URL 驗證時失敗。整合、工作流程與工作流程步驟則先去除空白，因此只含空白的值會被忽略，解析會繼續到專案、使用者或內建設定。

| 原語 | 環境覆寫 | 專案設定 | 使用者設定 |
| --- | --- | --- | --- |
| 擴充功能 | `SPECKIT_CATALOG_URL` | `.specify/extension-catalogs.yml` | `~/.specify/extension-catalogs.yml` |
| 預設集 | `SPECKIT_PRESET_CATALOG_URL` | `.specify/preset-catalogs.yml` | `~/.specify/preset-catalogs.yml` |
| 整合 | `SPECKIT_INTEGRATION_CATALOG_URL` | `.specify/integration-catalogs.yml` | `~/.specify/integration-catalogs.yml` |
| 工作流程 | `SPECKIT_WORKFLOW_CATALOG_URL` | `.specify/workflow-catalogs.yml` | `~/.specify/workflow-catalogs.yml` |
| 工作流程步驟 | `SPECKIT_STEP_CATALOG_URL` | `.specify/step-catalogs.yml` | `~/.specify/step-catalogs.yml` |

來源項目的形狀實際上為：

```yaml
catalogs:
  - name: team
    url: https://example.com/catalog.json
    priority: 10
    install_allowed: false
    description: Optional text
```

`name` 是顯示／出處資料，而不是用於遮蔽的內容識別字。

### 依範圍合併的套件組型錄

套件組依來源 `id`，跨內建、使用者與專案範圍合併來源：

1. 內建來源建立回退。
2. 使用者來源取代具有相同 `id` 的內建來源。
3. 專案來源取代具有相同 `id` 的使用者或內建來源。
4. 具有不同 ID 的來源保留在有效堆疊中。

最終堆疊依 `(priority, id)` 排序，因此來源 ID 是確定性的同分決勝者。套件組來源設定可透過 `.specify/bundle-catalogs.yml` 由專案寫入；呼叫端在載入堆疊時也可提供使用者設定目錄。套件組沒有環境覆寫。

套件組來源使用明確的政策列舉，而非布林值：

```yaml
schema_version: "1.0"
catalogs:
  - id: team
    url: https://example.com/bundles.json
    priority: 10
    install_policy: discovery-only
```

套件組來源支援的配置為 `https`、`file`、`builtin` 以及本機檔案系統路徑。其餘五種型錄類型接受遠端 HTTPS URL。六種類型都會在網路存取前拒絕純 HTTP 型錄來源，包括 localhost 與 loopback 位址。這是刻意的變更，移除了以往的本機開發 HTTP 例外，讓每個來源層都遵循相同的 HTTPS 政策。本機 HTTPS 開發伺服器需要 Python TLS 用戶端信任的憑證，採用其預設的 OpenSSL 信任設定，該設定可能與瀏覽器或作業系統的信任不同。`SSL_CERT_FILE` 可指定包含開發 CA 的 PEM CA 憑證套件。封存檔下載政策維持不變。

## 設定語意

六種原語的作用中堆疊讀取器都拒絕非對應的 YAML 根、非列表且非 null 的 `catalogs` 值，以及非對應的來源項目。驗證階段與接受的值除此之外有所不同：

- 取代層載入器會在讀取作用中堆疊時驗證遠端 URL。套件組解析會在具體化 `CatalogSource` 值時驗證來源結構，但套件組型錄命令讀取器的 `_read()` 只驗證外部設定形狀與結構描述版本。`add_source()` 會在附加之前，具體化並驗證既有項目，而 `remove_source()` 則刻意只依 ID 或 URL 篩選原始對應，不驗證其餘欄位。如此一來，使用者可以移除手動編輯過的無效來源，而不會被該無效項目困住。
- 工作流程與工作流程步驟型錄的移除，保留設定形狀與優先順序驗證，但跳過 URL 驗證。移除絕不會擷取來源，因此舊版 HTTP 項目不會阻擋移除該來源或不相關的 HTTPS 項目。探索與擷取仍要求 HTTPS。移除會保留優先順序，同分時以 YAML 宣告順序決勝。
- 所有讀取器都拒絕布林優先順序。除此之外，取代層載入器會呼叫 `int(value)`，因此 `1.9` 這類小數值會被截斷為 `1`。套件組 `CatalogSource` 具體化會拒絕布林值與浮點數，而不加以轉換，但 `_read()` 與 `remove_source()` 可在不具體化的情況下攜帶或移除這些原始值。
- 取代層載入器會在解析作用中堆疊時，拒絕格式錯誤的遠端 URL 與所有純 HTTP。套件組來源驗證依路徑而定：型錄命令會在寫入前驗證支援的配置與遠端安全性，而手動編輯的堆疊則在使用時由擷取器重新驗證。
- 預設集、工作流程、工作流程步驟與兩種套件組讀取器，都把 `catalogs: null` 視為不提供任何項目。擴充功能與整合則將其視為空的已選設定，並以失敗關閉。

目前的空設定行為刻意不一致：

| 原語 | 空文件／`null` | 缺少或空的 `catalogs` | 無可用 URL 的項目 |
| --- | --- | --- | --- |
| 擴充功能 | 錯誤 | 錯誤 | 錯誤 |
| 整合 | 錯誤 | 錯誤 | 錯誤 |
| 預設集 | 該層不提供任何內容 | 該層不提供任何內容 | 該層不提供任何內容 |
| 工作流程 | 該層不提供任何內容 | 該層不提供任何內容 | 當非空列表無可用 URL 時錯誤 |
| 工作流程步驟 | 該層不提供任何內容 | 該層不提供任何內容 | 當非空列表無可用 URL 時錯誤 |
| 套件組，解析讀取器 | 空文件不提供任何內容；明確的 `null` 格式錯誤 | 不提供任何內容 | 來源驗證失敗 |
| 套件組，設定命令讀取器 | 缺少／空文件回傳空的專案列表；明確的 `null` 格式錯誤 | 回傳空的專案列表 | 具體化項目時進行來源驗證 |

這些差異是歷史合約，而不是建議。未來的統一必須將任何語意變更明確化、另外審查，並作為行為變更涵蓋，而不是靜默正規化讀取器。

套件組設定為了向後相容接受缺少的結構描述版本，接受向前相容的 `1.x` 版本，並拒絕不支援的主要版本。其他來源設定檔目前沒有版本。

## 擷取、重新導向與快取行為

型錄酬載擷取是有界的，並在支援時使用儲存庫的已驗證 HTTP 輔助工具。遠端來源 URL 必須在使用前與重新導向後驗證。

目前行為依原語而異：

- 擴充功能與預設集使用每 URL 一小時的快取、為官方來源保留舊版快取名稱、驗證每個重新導向躍點、驗證快取酬載形狀，並將快取讀寫失敗視為盡力而為。
- 整合使用每 URL 一小時的快取，並在每個重新導向躍點以及變更後的終端 URL 上，套用其型錄專屬的 URL 驗證器。共用的 HTTP 重新導向處理常式也會在每個躍點上套用其嚴格的配置、主機與遠端至本機政策。整合會驗證快取酬載形狀、盡可能捨棄無效的快取項目，並將快取寫入視為盡力而為。
- 工作流程使用每 URL 一小時的快取、驗證每個重新導向躍點，並在傳輸、有界讀取、UTF-8 解碼或 JSON 解析錯誤後，回退到任何可讀的過期快取。初始 URL、重新導向與最終 URL 驗證的拒絕，會繞過過期快取回退，無論是由型錄驗證器或共用 HTTP 處理常式提出，並在其工作流程型錄錯誤中保留其原因。新解析的非物件酬載會在回退邊界之後被拒絕；合併前，酬載根必須是對應。
- 工作流程步驟遵循工作流程的快取／回退模型、驗證每個重新導向躍點，並在快取路徑包含符號連結時停用快取使用。重複的 JSON 欄位會在過期回退之前，重新以致命驗證錯誤提出；新解析的非物件酬載同樣會在回退邊界之後被拒絕。
- 套件組型錄擷取器不維護通用的遠端 TTL 快取。內建來源在線上時擷取儲存庫型錄，僅在型錄無法取得的失敗時回退到隨附的快照；格式錯誤或不安全的內容不會被快照掩蓋。套件組堆疊會在單一堆疊執行個體的生命週期內，記住已解析的酬載。擷取器在轉譯 HTTP 狀態錯誤時，會先關閉回應主體，再傳播型錄錯誤，同時保留原始例外作為其原因，並保留以狀態為基礎的回退分類。

未來的共用擷取邊界可共用 URL 驗證、重新導向驗證、有界讀取、快取記錄與錯誤型別。它必須保留每個原語的回退政策，直到另外核准獨立的行為變更。

上述工作流程與步驟 URL 政策行為是一項刻意的傳輸強化變更：在線上擷取期間，過期中繼資料不得掩蓋被拒絕的 URL 或重新導向，特別是當套件組依賴該結果來驗證參照時。過去，型錄回呼可能拒絕重新導向或最終 URL，卻仍回傳已過期的中繼資料。型錄與共用 HTTP 驗證器現在都會將這些拒絕保留為確定的型錄錯誤；一般的擷取失敗則保留既有的過期快取回退。共用重新導向處理常式會在 urllib 正規化格式錯誤的絕對目標或提出未分類的解析錯誤之前，先檢查原始 `Location` 與舊版 `URI` 標頭。有效的相對與配置相對重新導向，仍保留 urllib 的一般解析行為。

## 酬載驗證擁有權

共用來源層應擁有來源設定、擷取、快取機制與來源出處。原語仍負責其酬載結構描述與項目語意：

- 擴充功能型錄驗證 `extensions` 對應與擴充功能中繼資料
- 預設集型錄驗證 `presets` 對應與預設集中繼資料
- 整合型錄驗證 `integrations` 對應與整合中繼資料
- 工作流程型錄驗證工作流程記錄
- 工作流程步驟型錄驗證步驟記錄，包括重複識別字
- 套件組型錄驗證其結構描述版本與強型別套件組項目

領域驗證必須在安裝副作用之前進行。共用層不得將格式錯誤的酬載變成空的成功結果。

## 來源失敗

可復原的來源擷取錯誤可被擴充功能、預設集、整合、工作流程與工作流程步驟跳過，讓另一個所選來源仍可使用。驗證錯誤並非一致可復原：

- 擴充功能與整合會為失敗的來源發出警告，並在每個來源都失敗時擲出。由於整合發行歷程驗證發生在 `_fetch_single_catalog` 期間，格式錯誤的發行歷程會表示為 `IntegrationCatalogError`，因此合併會警告、跳過該來源，並可公開優先順序較低的副本。
- 預設集查找在沒有來源可讀時，保留第一個擷取錯誤；預設集搜尋會將可復原的擷取失敗（包括被拒絕的重新導向）轉換為空結果，即使沒有來源可讀，且不論來源順序。無效的來源設定（`PresetValidationError`）在搜尋中是致命的，且會在擷取前驗證，包括被拒絕的 HTTP 型錄 URL。`PresetCatalogValidationError` 仍為致命：即使在讀取有效的高優先來源後，搜尋仍可能因無效的低優先內容而失敗，而定向查找可在找到所請求的高優先項目後立即回傳。
- 工作流程與步驟合併會計算來源失敗次數，並在每個來源都失敗時擲出。工作流程步驟的重複 JSON 欄位與重複 ID 是致命驗證錯誤，而不是可跳過的來源擷取錯誤。
- 工作流程與步驟擷取可在廣泛的擷取路徑失敗後，使用可讀的過期快取資料，包括傳輸錯誤、有界讀取失敗、解碼失敗與格式錯誤的 JSON。所有 URL 政策拒絕都會繞過過期快取回退，包括強制重新整理期間，且不論哪個驗證器先拒絕該 URL。新解析的非物件酬載與步驟重複欄位錯誤，同樣不在該回退範圍內。

套件組查找依優先順序快速失敗：載入來源錯誤會停止操作。內建擷取回退在套件組擷取器內部處理，而不是在 `CatalogStack` 中跳過來源。

這些是可見的行為差異。共用層需要為每個呼叫端宣告來源失敗策略，而不是一個隱含的全域政策。

## 遮蔽、出處、搜尋與查找

對於來自可讀來源的格式正確項目，定義內容 ID 的最高優先來源獲勝。即使以下情況，低優先副本仍被遮蔽：

- 低優先副本符合搜尋查詢，而獲勝副本不符合
- 低優先副本允許安裝，而獲勝副本僅供探索
- 低優先副本包含獲勝副本所缺少的所請求歷史版本

搜尋必須描述查找／安裝會解析的同一個獲勝項目；它不得公開無法到達的被遮蔽項目。

格式錯誤項目的處理是既定的例外：

- 擴充功能、整合、工作流程與工作流程步驟在合併期間跳過非對應項目，因此格式正確的低優先副本可獲勝。
- 預設集搜尋跳過非對應項目並可顯示低優先副本，但定向的預設集查找／安裝將格式錯誤的符合項目視為致命，且不會繼續往下找。
- 套件組酬載解析拒絕格式錯誤的項目，而不是跳過它們。
- 整合發行歷程驗證發生在擷取時；無效的高優先來源會作為失敗來源被跳過，讓低優先副本及其安裝政策獲勝。

已解析／搜尋結果保留來源出處：

- 取代層型錄以 `_catalog_name` 與 `_install_allowed` 註解記錄
- 套件組回傳攜帶其 `CatalogSource` 的 `ResolvedBundle`，且具體化的項目記錄 `source_id` 與 `source_policy`

出處是安裝政策檢查與診斷所需的語意資料。它不是僅供呈現的中繼資料。

## 精確的歷史發行選擇

六種原語都支援從獲勝的格式正確項目中，選擇宣傳的目前版本或精確的歷史發行。選擇：

- 絕不會繼續往下找低優先來源
- 在目前選擇器接受的情況下，接受 PEP 440 等價拼寫
- 保留型錄宣傳的發行拼寫
- 具體化歷史發行欄位，而不繼承僅供目前版本使用的下載、總和檢查碼、相容性或類似中繼資料
- 當獲勝項目未宣傳所請求的發行時，報告或回傳「找不到」

格式錯誤的發行歷程是驗證失敗，但其失敗階段很重要。擴充功能、預設集、工作流程、工作流程步驟與套件組，在獲勝項目發行選擇失敗後，不會諮詢低優先來源。整合在擷取來源時驗證歷程，因此合併可跳過該來源並改選低優先副本。

## 預期的共用層邊界

`src/specify_cli/catalogs.py` 已提供狹窄的共用起點：`CatalogEntry` 與 `CatalogStackBase` 集中了來源項目欄位、遠端 URL 驗證與 YAML 設定載入。擴充功能與整合目前繼承該基底。預設集、工作流程、工作流程步驟與套件組保留獨立的來源模型與載入器，且六個領域的擷取、快取、合併、失敗、酬載與發行行為仍由原語擁有。

更廣泛的共用型錄領域，無論是在 `specify_cli.catalogs` 中演進，還是拆分為聚焦的相鄰模組，都可擁有：

- 型別來源身分、範圍、優先順序、信任／安裝政策與出處
- 具有明確空設定政策的設定解析原語
- 環境／專案／使用者／內建來源解析策略
- 穩定的來源排序與遮蔽
- 已驗證的有界擷取與逐躍點重新導向驗證
- 快取介面與明確選擇的過期／離線回退策略
- 來源失敗策略
- 一般的「獲勝來源優先」搜尋／查找協調

原語模組繼續擁有：

- 酬載與項目結構描述
- 發行中繼資料欄位與領域專屬驗證
- 安裝／下載規劃與副作用
- CLI 提示、警告、呈現與結束代碼
- MCP 結構描述、註解與通訊協定錯誤

共用層必須接受明確的專案與使用者路徑。它不得讀取可變的行程工作目錄狀態、提示、列印、從機器可讀模式推斷信任，或僅因來源可到達就使其可安裝。

## 移轉限制

重構到共用層必須漸進且保持行為不變：

1. 保持特徵矩陣通過。
2. 一次移動一個可獨立測試的事項。
3. 在測試或消費者依賴時，保留既有的匯入與 monkeypatch 路徑，包括 `specify_cli.catalogs.CatalogEntry`、`specify_cli.catalogs.CatalogStackBase`，以及建立在這些型別之上的擴充功能／整合套件匯出與子類別 patch 點。
4. 不要在結構性 PR 中正規化空設定、來源失敗處理、快取回退或信任預設值。
5. 將任何預期的正規化視為獨立的行為變更，並依[測試確定性行為](../CONTRIBUTING.md#測試確定性行為)提供正面與負面證據。
