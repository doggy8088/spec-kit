本期涵蓋 Spec Kit 在 2026 年 7 月的活動——這是強化基礎並擴大邊界的月份。共發布 28 個版本（v0.12.3 至 v0.15.1），橫跨三次次要版本升級，並帶來三項頭條功能：**`assess`「Idea Assessment Pipeline」擴充功能**，將規格驅動開發推向規格的*上游*，回答「我們到底該不該做這個？」；全新的 **`py`（Python）指令碼類型**，以及支撐它的廣泛 shell→Python 移植；以及供整合使用的**第一級代理原生執行階段事件層**。在功能之下，本月最主要的工程主題是持續的**安全性強化浪潮**——有界 HTTP 讀取、嚴格的重新導向驗證、消除 TOCTOU 競態，以及工作流程引擎全面的防禦性驗證。在外部方面，報導在結構上擴大了：主流科技媒體（heise online）以兩種語言報導 v0.13 的 `assess` 版本，**配套工具生態系**也在專案周圍蓬勃發展——規格↔程式碼漂移偵測器、模型尺寸顧問與測試缺口工具，全都建置*於* Spec Kit *之上*。下表為摘要，後文接續詳述。

### Idea Assessment Pipeline：`assess`

7 月的頭條功能是 **`assess` 擴充功能**（#3568），這是一條*想法評估管線*，以選擇性啟用的擴充功能形式發布，並將規格驅動開發向上游再推進一步，達到前所未有的位置。核心生命週期從 `/speckit.specify` 開始——假設建置決策已經做出——而 `assess` 處理的是規格*之前*的問題：**這個想法到底該不該建置，它是否已被充分理解到足以撰寫規格？**

該管線執行分階段流程——**capture → evidence → refine → design → decision**——接收原始想法、蒐集佐證、將其精煉為具體事物、勾勒設計，並以明確的 **go／clarify／kill** 判定收尾。`go` 會將成形的問題送入既有的 `/speckit.specify` 步驟；`clarify` 會退回要求更多資訊；`kill` 則在一行規格都還沒寫之前就停止工作。它的輸入只是一個想法——貼上的文字、URL、工單或程式碼庫指標——因此該管線**在空的、剛初始化的專案或既有程式碼庫上都能同樣良好運作**（#3732）；團隊能在任何鷹架存在之前評估一個全新想法，或針對已有程式碼庫的儲存庫評估一項變更。

這項功能獲得本月最受矚目的主流媒體報導：**heise online** 以英文與德文刊登了 *「From Idea to Spec: The New Feature in Spec Kit 0.13」*，將 `assess` 定位為 0.13 系列值得注意的新增功能，並與 Azure DevOps CLI 支援及 bundler／預設集驗證修正並列。由於來自歐洲主要科技媒體而非開發者部落格，這是 Spec Kit 的發布節奏現已被視為主流工具新聞追蹤的訊號。 [\[heise.de\]](https://www.heise.de/en/news/From-Idea-to-Spec-The-New-Feature-in-Spec-Kit-0-13-11371866.html)

### Python 遷移：`py` 指令碼類型

Spec Kit 在 7 月的第二個主題較為低調，但在結構上很重要：專案開始將其 shell 指令碼遷移至 **Python**。全新的 **`py` 指令碼類型**（#3285）與 `sh`（bash）、`ps`（PowerShell）並列，成為 `specify init` 的第三個選項，其背後是能跳過損壞殘存的 Python 直譯器解析（包含 Windows Store 的 `python3` 別名，#3385）。`py` 類型是專案對長年 bash／PowerShell 一致性稅的回答——以往每個指令碼修正都必須寫兩次並保持同步，這是過往數月更新日誌中 Windows 一致性錯誤反覆出現的來源。

在新類型背後，系統性移植在本月逐件落地：**`update-agent-context`** 更新工具（#3387）、**git 擴充功能指令碼**（#3400）、**`check-prerequisites`** 概念驗證（#3302），最後是三個核心指令碼——**`create-new-feature`、`setup-plan` 與 `setup-tasks`**（#3386）。wheel 已更新以隨附 `scripts/python`，因此 `--script py` 能從乾淨的 PyPI 安裝運作（#3665），安裝文件與 init 選項表也已更新，寫入新類型與 sh／ps 遷移計畫（#3284、#3640）。最終狀態是單一、跨平台的指令碼實作，消除了整整一類一致性錯誤。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 代理原生執行階段事件

v0.15.0 的頭條是**供整合使用的第一級代理原生執行階段事件層**（#3704）。它透過一組標準的 snake_case 事件名稱——`session_start`、`pre_tool_use`、`post_tool_use`、`user_prompt_submit`、`stop` 與 `session_end`——將 Spec Kit 橋接至宿主代理自身的生命週期。輕量、零相依性的 **Event Dispatcher**（`.specify/events.py`）會在 `specify init` 期間建立鷹架，逐整合的 **Event Adapters** 則將每個標準事件轉譯為代理的*原生* hook 設定——**Copilot CLI** 用 `.github/hooks/speckit.json`（bash／PowerShell 變體）、Claude Code 用 `.claude/settings.json`、Cursor 用 `.cursor/hooks.json`、Codex 用 `.codex/config.toml`、opencode 用 TypeScript 外掛，以及 Gemini、Qwen、Devin 與 Tabnine 的原生設定合併——因此擴充功能作者只需在 `extension.yml` 中宣告一次 `events:`，永遠不必學習代理專屬名稱。解析是四層堆疊（CLI `--events false` → 使用者 `.specify/integration-events.yml` 覆寫 → 擴充功能宣告的事件 → 內建預設值），且多個擴充功能宣告相同事件時都會執行。這項變更伴隨更廣泛的整合精煉：使用恆常斜線叫用的代理（Droid、Forge、Cline）現在能正確算繪連字號的 `/speckit-<name>` 命令（#3688、#3642、#3622），原生技能叫用前綴獲得保留（#3663），數個代理（kiro-cli、Lingma、Pi、omp）被宣告為可安全多次安裝。其主軸是整合日益*原生*於每個代理，而非最低公分母的覆蓋層。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 安全性強化浪潮

橫跨全部 28 個版本最主要的工程主題是**安全性與穩健性**。工作分為三個層面。**有界 I／O：** 每個型錄、下載與套件組 HTTP 回應現在都在位元組上限下讀取，並在每一次跳轉進行嚴格的重新導向驗證（#3140、#3671、#3763、#3141），封閉了一類無界讀取／DoS 暴露。**消除競態：** 檔案解除連結與狀態檔案處理中的 TOCTOU 競態已移除（#3811、#3815、#3819），擴充功能 URL 下載快取已強化以防範符號連結與連接點競態（#3869），登錄檔開啟已釘選至 UTF-8（#3810、#3816）。**注入與輸入強化：** `shell` 參數已從 `run_command` 移除（#3716），使用者提供的型錄中繼資料在每個探索／清單／`init` 輸出路徑中都經過逸出處理（#3772、#3773、#3774、#3806、#3826、#3863），且型錄 URL 在重新導向*之後*會重新驗證，以保留 HTTPS／主機保證（#3523、#3524）。

與此並行的是工作流程引擎與型錄載入器全面的系統性**「大聲失敗、不要當機」**行動：數十個 PR 將原始的 `ValueError`／`OverflowError`／當機路徑，替換為針對格式錯誤輸入的乾淨驗證錯誤——非字串命令、提示詞、整合與模型；非清單分支與 `wait_for` 條目；`priority: .inf` 與布林優先順序；非對應的資訊清單區塊；以及上標數字閘門提示詞。整個月的強化都以預防而非回應的形式到來。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 工作流程引擎與套件組走向成熟

除了強化之外，**工作流程引擎**持續獲得能力。步驟現在能讀取其**工作流程來源目錄**（#3469），shell 與提示詞步驟獲得**可設定、經驗證的逾時**（#3404、#3847、#3768），**閘門判定能透過 `verdict_input` 綁定至工作流程輸入**（#3725），**`WorkflowResolver`** 也被抽離為獨立元件（#3557）。兩個社群工作流程進入型錄——引導式的 **`pipeline`**（#3338，串連至核心 `/speckit.converge`）與 **`yolo`**（#3864）——使獨立工作流程數量達到兩個。

6 月導入的**套件組子系統**透過一長串正確性工作走向成熟——透過標準 POSIX arcname 實現可重現建置（#3658）、逐字 UTF-8 資訊清單傾印（#3660）、嚴格拒絕格式錯誤的 `requires`／`provides`／`integration`／`catalogs` 區塊，以及格式錯誤下載 URL 時乾淨的 `BundlerError`（#3586）。**社群套件組提交自動化**已落地（#3553），**SicarioSpec Security & Governance Bundle** 成為列入型錄的社群套件組（#3636），讓套件組在實務上成為可由社群提交的活產物類型。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 擴充功能與預設集生態系

社群擴充功能型錄在 7 月從 125 個成長至 **144 個條目**——淨增加 19 個。社群預設集從 23 個成長至 **29 個**，社群工作流程達到 **2 個**，第一個社群**套件組**（SicarioSpec）也列入型錄。

依類別列出的值得注意的新擴充功能：

- **驗證、漂移與證據**：Test Coverage Drift Control、PatchWarden Evidence Pack、Quality Gates (Enforcement Layer)、Verify Review Ship、Intent Reconciliation
- **需求與接收**：EARS Requirements Syntax、`assess` Idea Assessment Pipeline、Spec-Kit BDD、Charter
- **外部追蹤工具與來回同步**：Linear Weave、Multi-Repo Branch Sync、ContextForge MCP
- **設計與文件**：Spec Kit Figma、Figma Starter、Blueprint Index — Living Architecture Map、LLM Wiki、Dotdog
- **知識與協調**：OKF Knowledge Bundle Generator、Orchestration Task Context Management、Spec Kit Memory

型錄也展現強勁的維護活動：**DocGuard — CDD Enforcement** 歷經數個版本推進（至 v0.33.0），**Verify Review Ship** 與 **Quality Gates (Enforcement Layer)** 快速迭代，**Architecture Guard**、**Golden Demo**、**Coding Standards Drift Control**、**Ripple** 與 **Ralph Loop** 都發布了更新。預設集方面是本月最忙碌的：龐大的**治理預設集**家族擴大並迭代——**Autonomous Run Governance** 與 **Parallel Autonomous Run Governance** 預設集、完整的 **Intake** 治理套件（Authoring、Review、Sequencing）、**Test-First Governance**，以及 A11Y、Agent-Parity、Cross-Platform、iSAQB-Architecture、Architecture 與 Security 治理預設集的協調版本升級。 [\[github.com\]](https://github.github.io/spec-kit/community/extensions.html)

## SDD 生態系與產業趨勢

### 從工具到平台

7 月最清晰的生態系訊號是結構性的：對話從「我該如何使用 Spec Kit？」轉向「我該在其*周圍*建置什麼？」配套工具——artgraph 處理確定性漂移、SpecJudge 處理模型尺寸、GAUNTLEX 處理測試缺口，以及一組不斷成長的自訂代理技能——將 Spec Kit 的產物（憲章、規格、任務、執行狀態）視為穩定的基底來建置。公開社群型錄強化了這一點：在 144 個列入型錄的擴充功能中，最響亮的主題是驗證與品質（review、validate、drift、sync、verify、audit），核心 SDD 動詞日益被擴充功能*重新表達*，而非僅僅被覆寫——這是對可組合、可覆寫核心命令需求的證據。 [\[github.com\]](https://github.github.io/spec-kit/community/extensions.html)

### 競爭格局

「該選哪款 SDD 工具？」的比較仍是主要內容類型，但 7 月的框架收窄了：6 月的評測涵蓋七款工具，7 月最具實質內容的文章則日益正面對決 **Spec Kit 與 Kiro**（ta_kawano、[faruryo](https://qiita.com/faruryo/items/87a14728299e89f80ff4)、Towards AI）。反覆得出的結論維持不變——Spec Kit 是最重且最靈活的選項，在可衡量的 Success Criteria、需求引出與綠地拆解方面表現強勁，而其文件激增與認知負荷則是一致的取捨。收斂不變量分析（ranjankumar.in）更進一步，主張各框架正收斂至相同的結構基本元件，這將競爭問題從「哪款工具」轉向「哪個生態系與治理模式」。在這個軸線上，Spec Kit 不斷擴大的型錄、代理中立性，以及現正形成的配套工具層，是其差異化所在。 [\[note.com\]](https://note.com/takawano/n/ncb552ee37331)

## 路線圖

正在討論或進行中、供未來發展的領域：

- **規格的上游**——`assess` Idea Assessment Pipeline 在規格存在之前延伸 SDD。預期 capture→evidence→refine→design→decision 流程將深化，而隨著管線獲得實際使用，想法評估與 `/speckit.specify` 之間的界線將成為精煉的關鍵領域。 [\[heise.de\]](https://www.heise.de/en/news/From-Idea-to-Spec-The-New-Feature-in-Spec-Kit-0-13-11371866.html)
- **Python 遷移**——`py` 指令碼類型，以及核心指令碼、git 擴充功能與代理脈絡更新工具的移植，確立 Python 為擺脫 bash／PowerShell 一致性稅的路徑。完成移植並讓 `py` 成為慣用的預設值（而非 sh／ps）是其回報：一整類 Windows 一致性錯誤將消失。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **代理原生執行階段事件**——第一級事件層讓整合能透過標準事件名稱與逐代理適配器，將 Spec Kit 接入每個代理自身的執行階段。該層**正在積極演進**——早期訊號指向 opencode 脈絡注入與 JSON 信封代理 hook。預期更多代理將獲得事件適配器，擴充功能作者也將倚賴宣告式的 `events:` 介面，隨著整合層從最低公分母覆蓋層轉向真正原生的行為。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **Copilot 技能成為預設**——7 月在技能預設推出之前發布了警告，訊號現在指向**預設翻轉正在進行**——將 `specify init --integration copilot` 移至技能版面配置，並讓預設 init 整合能透過環境變數覆寫，markdown 命令版面配置則成為舊有路徑。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **Copilot 原生介面**——第一方 [`github/spec-kit-copilot`](https://github.com/github/spec-kit-copilot) 儲存庫（列名的社群夥伴）將 `specify` CLI 包裝為 **Copilot 技能外掛**（九項技能，涵蓋設定、init、擴充功能、預設集、套件組、工作流程與自我升級），供 Copilot CLI 與 App 使用，並與 CLI v0.15.0 對齊。新興方向是**視覺化、由 Copilot 驅動的介面**——早期工作探索 Spec-Driven Development 流程的畫布儀表板、Bug Fix Pipeline 與 `assess`——將 CLI 的流程轉為互動層。 [\[github.com\]](https://github.com/github/spec-kit-copilot)
- **配套工具層**——artgraph、SpecJudge、GAUNTLEX 與自訂技能，顯示第三方生態系正在 Spec Kit 產物上形成。懸而未決的問題是專案是否吸收這些模式（如同它曾將 drift → `converge` 一樣），還是留給生態系；擴充功能型錄中對驗證／漂移的需求顯示上游拉力持續存在。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **安全性與穩健性成為常設紀律**——7 月的強化浪潮（有界讀取、嚴格重新導向、消除 TOCTOU、大聲失敗驗證）從功能轉為例行，訊號指向它**將作為持續行動延續**——為 stdin 讀取設上限以封閉 DoS 路徑，以及更廣泛的原子性推動（原子暫存檔寫入、子行程逾時、結構化記錄與縮小範圍的例外處理常式）。隨著介面（bundles、workflows、catalogs、events）成長，維持無無界讀取的不變量是持續的工作。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **體驗簡化**——文件激增與認知負荷仍是 7 月持平評論中最常被提及的單一疑慮（ta_kawano、yutakaosada，以及多篇日文／韓文文章）。`assess` 上游閘門、精簡／TinySpec 預設集、`/speckit.converge` 與正在形成的配套工具層都提供了解答；將它們呈現給新使用者是持續的機會。 [\[note.com\]](https://note.com/takawano/n/ncb552ee37331)
