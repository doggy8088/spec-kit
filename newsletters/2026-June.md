## Spec Kit 專案更新

### 版本總覽

**v0.9.0–v0.9.5**（6 月 1–5 日）以一次次要版本升級與五個修補版本揭開本月序幕。頭條功能是 **原生 Cline 整合**（#2508）與 **rovodev** 支援（#2539），以及將代理脈絡更新抽離為隨附且可選擇性啟用的 **`agent-context` 擴充功能**的長期工作（#2546，關閉 #2398）。CLI 新增 **`specify self upgrade`**（#2475）與 **`extension add` 的 `--force` 旗標**（#2530）。工作流程引擎獲得四項能力：能在**沒有專案的情況下**執行 YAML 檔案（#2825）、在恢復執行時接受**更新後的輸入**（#2815）、在 `run`／`resume`／`status` 全面提供**結構化 JSON 輸出**（#2814），以及用於不中斷失敗的 **`continue_on_error` 步驟欄位**（#2663）。Windows 相容性也獲得強化，包含 UTF-8 stdout／stderr（#2817），且 cursor-agent 無頭調度現在能端對端運作（#2631）。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 收斂迴圈：`/speckit.converge`

**`/speckit.converge`**（#3001）是自核心命令本身以來，SDD 工作流程最重要的新增功能。它增加第九個步驟，在 `/speckit.implement` *之後*執行，並回應該專案每一篇評論中最常被提及的疑慮：*程式碼是否真的符合規格？*

Converge 會將 `spec.md`、`plan.md` 與 `tasks.md` 視為**唯一的意圖來源**——並以憲章作為治理約束——評估程式碼的目前狀態，並將任何尚未完成的工作以新的、可追溯的任務形式附加。它刻意**不是** diff 或 git 工具：它評估的是程式碼相對於功能產物的*目前*狀態，不做分支比較，也不看歷史紀錄。發現會依**缺口類型**分類——`missing`（完全缺失）、`partial`（存在但不完整）、`contradicts`（與意圖或憲章 MUST 衝突）或 `unrequested`（規格從未要求的工作）——並依嚴重程度分級，其中違反憲章 MUST 的情況永遠為最高等級。

其決定性的設計選擇是**僅附加、永不重寫**。它唯一的寫入是在 `tasks.md` 底部新增一個 `## Phase N: Convergence` 區段；它永不修改規格或計畫，永不重新編號既有任務，也永不觸碰應用程式碼——完成附加任務仍是 `/speckit.implement` 的工作。當程式碼庫已滿足一切要求時，它會讓 `tasks.md` 逐位元組保持不變，並僅回報 **「✅ Converged.」** 每個附加任務都帶有 `source-ref`（例如 `FR-003`、`SC-002`、`US1/AC2`、計畫決策或憲章條文），保留從需求到修復的可追溯性。

其成果是一個**迭代式收斂迴圈**——converge → implement → converge——持續執行直到沒有缺口為止。它也透過為 Spec Kit 提供第一級的驗證與補齊缺口步驟（#2673），讓從 OpenSpec 遷移更為順暢，直接回應社群一直透過 Architecture Guard、Spec Trace 與各種漂移控制工具等擴充功能所表達的漂移與驗證需求。該命令現已記錄於快速入門與演進中規格指南中。 [\[github.com\]](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)

### 套件組子系統：`specify bundle`

6 月的第二個頭條是 **bundles** 的首次亮相（#3070），這是一個位於既有基本元件之上的發行與組合層。擴充功能、預設集、工作流程與步驟是積木，而**套件組是一個經過策劃、具版本、以角色為基礎的堆疊**，宣告團隊或角色所需的一切，並以單一步驟安裝。關鍵在於，套件組*本身不增加任何新的執行階段行為*——它透過每個元件各自的機制組合既有內容，因此在執行時沒有新東西需要學習。

套件組由 **`bundle.yml` 資訊清單**描述：中繼資料（`id`、`name`、`version`、`role`、`author`、`license`）、`requires` 區塊（最低 `speckit_version`、工具、MCP 伺服器），以及 `provides` 區塊，列出它所安裝的確切擴充功能、預設集（附 `priority` 與組合 `strategy`）、步驟與工作流程——每個都釘選至特定版本。首批範例套件組提供四種角色：**developer、product-manager、business-analyst 與 security-researcher**。

子命令介面提供完整的套件管理體驗：`search` 與 `info`（會在安裝前預覽**完整展開的元件集合**，附釘選版本與 `verified` 對 `community` 的信任指標）、`install`、`update`（`--all`）、`remove`、`list`、`init`、`validate`、`build`（產生單一具版本的 `.zip` 產物）、`publish`，以及 `catalog` 管理（`list`／`add`／`remove` 來源）。安裝具**冪等性且完整追蹤來源**，因此套件組日後能乾淨地移除或刷新；`remove` 只會解除安裝某套件組所貢獻的元件，讓其他已安裝套件組仍需要的任何元件保持原位。若在尚未是 Spec Kit 專案的目錄中執行，`install` 與 `init` 會**先啟動一個專案**，因此全新簽出的程式碼能以單一命令達到可運作狀態。安裝時唯一檢查的跨套件組衝突點是作用中的整合。

套件組透過與其他所有元件相同的優先順序目錄堆疊（專案、使用者與內建範圍）被發現，到了月底，它們已透過專門的提交路徑（#3162），成為繼擴充功能、預設集與工作流程之後的**第四種可由社群提交的產物類型**。套件組正是專案對「如何發行整套角色設定？」這個問題的回答——這是將整個目錄串連起來的可組合性故事。 [\[github.com\]](https://github.com/github/spec-kit/blob/main/docs/reference/bundles.md)

### 工作流程引擎走向成熟

除了 converge 與 bundles 之外，6 月也是**工作流程引擎成長**的月份。**步驟目錄**（#2394）讓步驟可由社群發行；**`init` 步驟**（#2838）讓工作流程能啟動專案；**JSON 輸出**（#2963）與 **`from_json` 篩選器**（#2961）讓步驟輸出能以具型別資料的形式被取用；**`bug-assess`** 代理工作流程（#3023）則成為第一個建置於該引擎之上、正式發布的端對端自動化。月底的強化加入有界並行扇出（#3224）、能感知引號的運算式解析（#3232、#3197）、更嚴格的閘門與 `wait_for` 驗證（#3233、#3225），以及失敗或中止執行時正確的非零結束碼（#2959）。這個起初是固定七步驟序列的引擎，現在已是可程式化、可由社群擴充的自動化基底。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 架構與重構

**`__init__.py` 拆解系列**在 6 月從 4／8 推進至 **7／8**。PR 5／8 將整合命令集中至 `integrations/` 領域目錄（#2720），PR 6／8 將預設集命令處理常式抽離至 `presets/_commands.py`（#2826），PR 7／8 將擴充功能命令處理常式移至 `extensions/_commands.py`（#3014）。系統性的抽離持續改善貢獻者上手體驗與測試隔離，目前只剩一個部分。已移除的 HTTP 輔助函式（`open_github_url`、`_StripAuthOnRedirect`）是在預設集 URL 安裝強化之後接續移除的（#2883）。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 錯誤修復與安全性

25 個版本帶來密集的修復節奏，集中於**跨平台一致性**與**工作流程穩健性**。Windows／PowerShell 獲得最多關注：PowerShell 5.1 init 卡住問題（#2938）、UTF-8 stdout／stderr（#2817）、`check-prerequisites.ps1` 的 stderr 路由（#3123）、區分大小寫的分支名稱縮寫一致性（#3129），以及數個 bash 一致性指令碼修正（#3196、#3198、#3230、#3231）。工作流程正確性獲得改善，包含對未知運算式篩選器大聲失敗（#3074）、拒絕幻影權限閘門（#3079），以及保留引號清單字面值內的逗號（#3134）。長期存在的錯誤也獲得關閉，包含 233 天的 worktree 分支編號重複問題（#1066）與整合升級時的擴充功能命令註冊缺口（#2886）。

安全性與供應鏈工作是本月的一大主題。**預設集 URL 安裝已強化以防範不安全的重新導向**（#2911）、**`run_command` 現在會拒絕 `shell=True`**（#3132）、**命令註冊路徑處理已強化**（#3088）、**CI 動作已釘選至 commit SHA 並加入 shellcheck**（#3126）、**目錄封存檔在安裝前會以 sha256 驗證**（#3080）、**擴充功能自我安裝路徑不再能刪除其來源目錄**（#2991）、**單一擴充功能的失敗會被隔離**，因此一個不良擴充功能不會拖累其餘部分（#2951），且**無主機的目錄 URL 現在會被拒絕**（見於基底與預設集驗證器，#3209）。 [\[github.com\]](https://github.com/github/spec-kit/releases)

### 擴充功能與預設集生態系

社群擴充功能目錄在 6 月從 105 個成長至 **124 個條目**——四週穩定增加 19 個。社群預設集從 21 個成長至 **23 個**。

依類別列出的值得注意的新擴充功能：

- **驗證與漂移**：Golden Demo 可執行參考與行為漂移偵測、Coding Standards Drift Control、Spec Trace 規格至程式碼可追溯性
- **外部追蹤工具與來回同步**：Linear 整合（`spec-kit-linear`）、透過同步引擎的 Jira Integration、Tasks to GitHub Project
- **自主與迴圈**：Loop Engineering（安全的 maker／checker 代理迴圈）、Research Harness
- **權杖與脈絡經濟**：Token Economy（路由、實測節省、脈絡稽核）
- **可見性與產物**：Spec Kit TLDR 審查儀表板、Data Model Diagram（Mermaid ER 圖）、Spec Roadmap
- **接收與探索**：Improve（將程式碼庫稽核為具優先順序的規格提示詞）、Intake（結構化需求接收）、Spec Kit Discovery
- **多專案**：Multi-Sites Spec Kit、RAG Azure Builder、SpecKit Companion

目錄也展現強勁的維護活動：**Linear Integration** 歷經數個版本推進（至 v0.7.0），**DocGuard — CDD Enforcement** 進展至 v0.28.0，**Superpowers** 橋接持續快速迭代，**Architecture Guard**、**Security Review**、**Product Forge**、**MemoryLint** 與 **Multi-Model Review** 都發布了更新。新預設集包含 **Command Density** 與 **SicarioSpec Core**，治理預設集家族（a11y、agent-parity、cross-platform、iSAQB-architecture、architecture、security）也獲得一輪協調更新。 [\[github.com\]](https://github.github.io/spec-kit/community/extensions.html)

### Microsoft 的第一方背書

**6 月 10 日**，**Microsoft Developer Blog** 發布了 *「Spec-Driven Development: A Spec-First Approach to AI-Native Engineering」*，作者為 Apoorv Gupta（Microsoft 首席軟體工程師）——這是第一篇由非維護者撰寫的第一方文章，介紹 SDD 並將 **GitHub Spec Kit 定位為讓其落地實作的工具包**。該文涵蓋七步驟生命週期，並走訪三個真實的綠地與棕地案例研究，將其實踐提煉為單一一句話：**「spec quality = output quality.」** 由於來自 Microsoft 自家的開發者平台而非維護者，這是本月最清晰的訊號，顯示規格驅動開發已從社群實驗走向獲得機構背書的實踐。 [\[developer.microsoft.com\]](https://developer.microsoft.com/blog/spec-driven-development-ai-native-engineering)

## SDD 生態系與產業趨勢

### 品類正在整合

在 6 月廣泛的文章報導中，一致的框架浮現：規格驅動開發現在已是成熟的品類，而 Spec Kit 是其參考實作。SSOJet 稱其為「品類錨點」，Design News 與多篇比較文章稱其為代理中立的預設選擇，ToolTwist 的高階主管指南則稱其為「擴展中團隊的安全預設選擇」。Microsoft Developer Blog 的文章與 SNCF 企業訪談，將這個框架從開發者媒體延伸至機構與企業脈絡。 [\[ssojet.com\]](https://ssojet.com/blog/best-spec-driven-development-tools)

### 競爭格局

「該選哪款 SDD 工具？」的比較成為 6 月最主要的內容類型，幾乎總是出現相同的陣容：**Spec Kit、OpenSpec、Superpowers、BMAD、Kiro、Tessl 與 GSD**。來自 ToolTwist、BrainGrid、Particula Tech 與眾多多語言評測反覆得出的結論是，*實踐*比工具更重要，其中 Spec Kit 被定位為可攜、社群驅動、代理中立的預設選擇，競爭者則在棕地人體工學與漂移管理上做出差異化。持平的評論對取捨有一致的看法：Spec Kit 是最重且最靈活的選項（30 個以上代理、完整的憲章／生命週期模型），這既帶來最廣泛的能力介面，也帶來最多的審查負擔。實作評分文章（ypyl、vc.ru）給予它在綠地與多情境工作上的高分，在研究任務與漸進式棕地編輯上分數較低——這正是 `/speckit.converge` 迴圈與不斷成長的棕地／漂移擴充功能生態系所要補齊的缺口。 [\[tooltwist.com\]](https://tooltwist.com/insights/spec-driven-frameworks-cxo-guide)

## 路線圖

正在討論或進行中、供未來發展的領域：

- **收斂迴圈**——`/speckit.converge`（#3001）是核心對幾乎每篇評論都提出的漂移與驗證疑慮的直接回應。預期僅附加的收斂模式將持續深化，社群漂移／驗證擴充功能（Golden Demo、Spec Trace、Coding Standards Drift Control）也將持續把需求回饋至上游。 [\[github.com\]](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)
- **套件組子系統**——`specify bundle`（#3070）將以角色為基礎的發行確立為第一級基本元件。隨著社群提交路徑現已開放（#3162），且四種範例角色已發布，策劃、信任訊號（`verified` 與 `community`）與版本釘選強制執行，將成為接下來要成熟的領域。 [\[github.com\]](https://github.com/github/spec-kit/blob/main/docs/reference/bundles.md)
- **可程式化的工作流程平台**——有了步驟目錄、JSON 輸出與 `from_json` 篩選器，工作流程現在可由社群擴充並可撰寫指令碼。懸而未決的問題是可發現性與拉力：步驟目錄還很新，採用情況將顯示獨立的工作流程撰寫是否會成為真正的生態系，還是停留在進階使用者的小眾領域。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **PyPI 發布**——發布工作流程與 README 中繼資料已落地（#2915，關閉 #2623），但官方 PyPI 發行尚未成為建議的安裝路徑；`uv tool install` 與 git 仍是標準方式。完成並強化這一點，能減少受限／隔離網路環境的摩擦。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **CLI 架構清理**——`__init__.py` 拆解已達 7／8（extensions/_commands.py，#3014），只剩一個部分。其回報是貢獻者上手體驗與測試隔離。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **邁向穩定版本**——v0.10.0 移除 `--no-git` 且 git 擴充功能改為選擇性啟用，是第一個真正的破壞性變更，而推進至 v0.12 反映了 1.0 之前持續的動能。隨著介面（bundles、workflows、converge）逐漸穩定，預期 API 將持續穩定化。 [\[github.com\]](https://github.com/github/spec-kit/releases)
- **體驗簡化**——審查負擔、小型任務的繁瑣流程與冗長的 markdown 輸出，仍是 6 月持平評論中最常被提及的疑慮（Particula Tech、ypyl、vc.ru，以及多篇韓文與日文文章）。精簡預設集、TinySpec、`/speckit.converge` 與角色套件組都提供了解答；將它們呈現給新使用者是持續的機會。 [\[particula.tech\]](https://particula.tech/blog/spec-driven-development-tools-spec-kit-vs-kiro-vs-tessl)
