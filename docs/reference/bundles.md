# 套件組

套件組將既有的 Spec Kit 元件（擴充功能、預設集、工作流程與步驟）組合成單一、具版本、可安裝的單位。擴充功能與預設集是基礎建構元素，套件組則是經過策劃的組合，宣告團隊或角色所需的完整內容，並透過各元件自身的機制在一個步驟內完成安裝。套件組本身不新增任何執行期行為：它只是疊加在您已在使用的基礎建構元素上的發佈與組合層。

套件組由 `bundle.yml` 資訊清單描述，並透過與其他元件相同的型錄堆疊來探索。安裝套件組時，系統會依釘選版本解析其宣告的元件，檢查作用中整合與共用元件版本的衝突，並以冪等方式套用每個元件，同時完整追蹤溯源資訊，以便日後能乾淨地移除或重新整理。

如需具體的入門範例，請參閱
[套件組資訊清單範例](https://github.com/github/spec-kit/tree/main/examples/bundles)
，涵蓋產品經理、業務分析師、安全研究人員與開發人員等角色。
這些範例展示的是以角色為基礎的設定封裝，而非填入內容的功能
規格；如需端到端使用範例，請參閱
[社群逐步教學](../community/walkthroughs.md)。

## 官方套件組

Spec Kit 在 `bundles/catalog.json` 中隨附官方套件組型錄。這些套件組經過策劃、標記為 `verified: true`，並透過內建的 `builtin://default` 型錄來源解析。

| 套件組    | 角色        | 元件                                            | 使用案例                                |
| --------- | ----------- | ----------------------------------------------------- | --------------------------------------- |
| `bugfix`  | `developer` | `bug` 擴充功能 + `bugfix` 工作流程                   | 引導式評估 → 關卡 → 修復 → 測試       |
| `assess`  | `developer` | `assess` 擴充功能 + `assess` 工作流程                | 在規格驅動開發之前先進行構想分流 |

安裝官方套件組的方式與安裝任何套件組相同（`add` 是 `install` 的別名）：

```bash
specify bundle install bugfix
specify bundle add assess
```

官方型錄會從線上的儲存庫擷取，在離線時則退回使用封裝在 wheel 中的快照，因此探索功能無需網路存取也能運作。本地套件組資訊清單可以使用 `--offline` 安裝隨附的擴充功能與工作流程。透過型錄探索的套件組資訊清單仍會從其 `download_url` 解析，因此 `specify bundle add <id>` 目前需要網路；完整的離線型錄安裝已列為後續工作。

## 搜尋可用的套件組

```bash
specify bundle search [query]
```

| 選項      | 說明                  |
| ----------- | ---------------------------- |
| `--offline` | 不存取網路    |
| `--json`    | 輸出機器可讀的 JSON   |

在所有作用中的型錄中搜尋符合查詢的套件組。未提供查詢時，會列出每個可用的套件組及其版本、角色、來源與信任指標（組織策劃的型錄項目為 `verified`，其餘為 `community`），讓您在安裝前判斷其可信度。

## 套件組資訊

```bash
specify bundle info <bundle_id>
specify bundle info <bundle_id> --versions
```

| 選項       | 說明                       |
| ------------ | --------------------------------- |
| `--offline`  | 不存取網路         |
| `--json`     | 輸出機器可讀的 JSON        |
| `--versions` | 列出目前與歷史型錄發行版本 |

顯示套件組的完整中繼資料，以及它會安裝的**完整展開元件集合**：每個擴充功能、預設集、步驟與工作流程及其釘選版本，外加預設集優先級與策略。輸出也包含信任指標（`verified` 與 `community`），讓您在安裝前判斷其可信度。這個預覽與 `install` 實際套用的計畫相同，因此您可以在提交前精確看到將新增的內容。對於含有引用的套件組，文字輸出會包含 `References` 摘要，列出每個被引用套件組自身的信任等級（`verified` 或 `community`），並標示被引用元件的最短來源鏈；被覆寫的元件會顯示被覆寫的版本與來源。JSON 會新增 `references` 項目，包含 `id`、`version`、解析後的 `source`、`install_policy`、`via`，以及被引用套件組自身的 `verified` 與 `trust`；對於含有引用的套件組，元件項目在資訊清單有宣告時也會包含 `source`（平面套件組會省略此欄位）、元件來自被引用套件組時的 `origin`（貢獻該元件的套件組鏈），以及每當該項目取代其他宣告時出現的 `overrides`，包括取代父套件組自身宣告的情況（此時沒有 `origin`）。每個 `overrides` 項目都帶有被取代的 `version` 與 `origin`，外加任何 `source`、`priority` 或 `strategy`；覆寫項目會列出宣告被取代值的每個不同套件組（保留通往各套件組的最短路徑），而非僅列出第一條路徑。僅供探索的引用會標記為 `discovery-only, not installable`。此處也會呈現與已安裝套件組已要求的元件之間可預見的重疊與版本衝突；套件組可以要求某個元件，但不一定已安裝該元件。

使用 `specify bundle info <bundle_id> --versions` 可以檢查型錄歷史，無需下載套件組資訊清單。搭配 `--json` 時，它會輸出套件組 ID、可用版本、目前版本、來源與安裝原則。

## 安裝套件組

```bash
specify bundle install <bundle_id | path>
```

| 選項           | 說明                                                         |
| ---------------- | ------------------------------------------------------------------ |
| `--integration`  | 覆寫初始化／安裝時使用的整合         |
| `--offline`      | 不存取網路                                          |
| `--refresh`      | 從所提供的套件組來源重新整理自有元件           |
| `--version`      | 安裝精確的歷史或目前型錄發行版本             |

透過每個基礎建構元素自身的機制，安裝套件組完整的元件集合。參數可以是型錄中的套件組 ID，或是本地路徑，指向已建置的 `.zip` 封存檔、套件組目錄或 `bundle.yml` 檔案；本地來源會直接安裝，不查詢型錄堆疊，除非資訊清單宣告了 `provides.bundles`。本地父套件組若含有套件組引用，會在命令執行時透過型錄堆疊解析那些子套件組，因此需要型錄與網路存取（參閱[套件組引用](#bundle-references)）。

若目前目錄尚未是 Spec Kit 專案，`install` 會先初始化一個專案，讓全新檢出的程式碼能在單一命令內達到可運作狀態。`--integration` 會在初始化新專案時選取整合，並在套件組釘選了特定整合但專案的作用中整合無法判定時（`.specify/integration.json` 缺失或無法讀取）確認目標。它**不會**覆寫已初始化專案的作用中整合：若套件組的目標整合與專案不同，安裝會中止且不做任何變更。與整合無關的套件組會繼承專案的作用中整合。未加上 `--refresh` 時，安裝是冪等的：已安裝且符合釘選版本的元件會跳過，套件組自有且相容的封裝修補發行版本也會跳過並發出警告（參閱下方說明）。其他版本不同或缺失的已安裝版本無法滿足釘選要求。只有 `--refresh` 能修復完全由本套件組擁有的漂移版本；獨立安裝的元件會跳過，且永遠不會被收編或取代。失敗時，不會寫入任何溯源記錄（安裝失敗即不記錄任何內容），該次執行期間安裝的元件會以盡力而為的方式移除：移除錯誤會被吞沒，因此磁碟上可能殘留部分狀態。

已安裝套件組的記錄會將要求的元件釘選與貢獻的元件分開儲存。相容的獨立安裝元件可以滿足套件組的要求，但仍保持獨立擁有：其釘選仍會阻止後續套件組安裝不相容的版本，而移除該套件組不會解除安裝該元件。未釘選的安裝或重新整理無法取代另一個套件組以釘選版本要求的元件；共用已安裝的相符版本且不重新整理仍是允許的。共用套件組在安裝或重新整理共用元件之前，還必須就元件來源達成一致，對於預設集則還包括優先級與策略。沒有要求清單的舊記錄會保留其已知的貢獻釘選；請重新安裝或重新整理套件組，以記錄其完整要求。

一般安裝會拒絕變更已記錄套件組的版本或自有元件中繼資料（版本、來源、預設集優先級或策略），包括移除自有元件。即使本地資訊清單保持相同的套件組版本，此規則同樣適用。重新排序未變更的元件或新增元件不需要重新整理。若要將變更套用到本地套件組而不將其加入型錄，請連同修訂後的來源加上 `--refresh`：

```bash
specify bundle install ./new-release/bundle.yml --refresh
```

來源也可以是套件組目錄或 `.zip` 封存檔。重新整理使用與 `bundle update` 相同的基礎建構元素更新路徑，重新套用套件組擁有的元件，並移除新資訊清單中省略的先前自有元件，除非另一個套件組仍需要它們。獨立安裝的元件保持不變，也不會被收編。成功摘要會包含重新整理與移除的數量。套件組記錄只會在操作成功後才前進；與 `bundle update` 相同，在重新整理失敗期間已修改的已安裝元件不會復原。

本地套件組來源提供的是資訊清單，而非其元件酬載。透過型錄解析的元件即使已安裝，重新整理時仍需要網路存取。只有當要安裝或重新整理的元件隨 Spec Kit 一起提供時才加上 `--offline`；否則命令會回報哪個元件需要網路存取。請在不加 `--offline` 的情況下重新執行，透過其型錄擷取該元件。

**封裝修補相容性。** 當隨 CLI 一起提供的擴充功能、預設集或工作流程，在釘選的主版本／次版本範圍內有較新的穩定修補發行版本時，安裝與重新整理會發出警告並使用該封裝版本。例如，釘選 `bug` 為 `1.0.0` 的套件組可以使用封裝的 `bug` `1.0.1`，無需編輯其資訊清單。驗證時會回報相同的警告。降級、主版本／次版本不符，以及預發行版本不同仍視為錯誤；明確的元件 `source` 也會保留精確釘選的強制執行。透過型錄解析的元件仍需要精確相符。這個例外提升了 CLI 升級之間的相容性，但修補發行版本並不保證行為不變。

套件組記錄會在 `required_components` 與
`contributed_components` 中保留要求的版本，並將實際已知的已安裝版本儲存在 `installed_versions` 下，以 `kind:id` 為鍵（例如 `"extensions:bug": "1.0.1"`）。這些內容也會在
`specify bundle list --json` 中顯示。不支援元件版本範圍、`latest`，以及省略擴充功能版本。

> **步驟酬載僅透過步驟型錄解析。** 套件組的 `provides.steps` 項目仍僅透過作用中的步驟型錄解析。套件組本地的 `steps/<id>/` 酬載與相對的 `provides.steps[].source` 覆寫，在此發行版本中**不會**被解析，因此以該方式宣告的步驟無法離線安裝。若要在今日隨套件組一起提供步驟，請將其發佈到套件組使用者可存取的步驟型錄。

## 套件組引用

套件組可以在 `provides.bundles` 中以精確、釘選的引用組合其他套件組。非空的引用清單需要資訊清單結構描述 `1.1`；空清單或 null 清單視為沒有引用。每個引用包含一個套件組 ID、一個精確的 SemVer `version`，以及一個可選的 `source`，用來命名預期勝出的套件組型錄（不是 URL）。引用 ID 是安全代稱，在資訊清單內必須唯一，且不能與父套件組同名：

```yaml
schema_version: "1.1"
bundle:
  id: team
  name: Team setup
  version: 1.0.0
  role: developer
  description: A team bundle
  author: Example team
  license: MIT
requires:
  speckit_version: ">=0.1.0"
provides:
  bundles:
    - id: bugfix
      version: 1.0.1
      source: default
    - id: qa-pack
      version: 2.0.0
```

引用會在命令執行時透過有效的套件組型錄堆疊解析。堆疊的勝出項目會依每個精確釘選選取；明確的 `source` 是一種斷言，表明這就是勝出的型錄，而非要求變更優先順序；不符即為錯誤，且不會退到另一個型錄。來自僅供探索來源的被引用套件組可以透過 `info` 檢查，但 `install`、`update` 與線上 `validate` 會將其拒絕為不可安裝。每次展開中，每個套件組 ID 只能有一個版本；循環以及同一 ID 出現第二個版本都是錯誤。若要解決第二個版本的衝突，請選取在該版本上達成一致的引用套件組發行版本。

展開的結果是單一平面元件計畫。被引用的套件組會依宣告順序以遞迴方式（深度優先）走訪，接著是宣告套件組自身的元件，同時保留既有的擴充功能、預設集、步驟與工作流程分組。每個 `kind:id` 最多安裝一次。當元件的版本與 `source` 相符時，副本即視為一致（省略與設定 `source` 的值視為不同）；擴充功能與預設集副本還必須具有相同的 `priority`，預設集副本還必須具有相同的 `strategy`。擴充功能可以省略 `priority`；省略的值表示預設值 `10`，因此與明確的 `10` 一致。預設集必須宣告整數 `priority`。同層引用之間的其他差異屬於衝突，必須在父套件組中修正。在每個層級，套件組自身的宣告優先於其引用，佔據宣告的位置，並發出描述覆寫及其來源鏈的警告。

展開最多允許 10 層引用巢狀與 50 個不同的被引用套件組 ID（不含根套件組）。循環會連同其引用鏈一起被拒絕。在安裝與更新時，系統會針對圖中的每個套件組檢查 Spec Kit 版本要求，不相容的要求是硬性錯誤，而根套件組仍是唯一的整合關卡：被引用套件組不同或未知的整合只會產生警告。`requires.tools` 與 `requires.mcp` 會在整個圖中取聯集，並透過既有的工具與 MCP 警告呈現。

已安裝的父記錄包含展開後的元件集合，以及一個可選的 `bundle_references` JSON 鍵，列出每個直接與遞移引用（各出現一次）及其解析後的型錄來源。不存在子套件組記錄。`bundle update` 會遵從父套件組目前的資訊清單及其釘選引用；移除與重新整理則保留既有的擁有權與元件生命週期規則。

被引用的資訊清單需要網路存取。對於本地根資訊清單，`install` 可以識別第一個引用，並在離線時以該引用名稱回報失敗。透過型錄的根 `install`、`info` 或 `update` 則可能更早失敗，在擷取其型錄或根資訊清單時就失敗，此時尚無法得知任何引用。`validate --offline` 會針對每個已宣告的引用各警告一次，說明該引用未被展開。`bundle build` 只會對引用執行結構檢查，不會解析或嵌入它們。

**已知限制。**

- 不支援被引用套件組的離線與本地解析；被引用的資訊清單需要有網路支援的型錄下載。
- 官方套件組型錄不保留發行歷史，因此對官方套件組的精確釘選，可能在該套件組發佈下一個發行版本時失效。
- 含有引用的本地套件組無法使用 `bundle info` 預覽；本地預覽已延後。
- 更廣泛的結構描述版本控制與 CLI 相容性檢查／範圍已延後。

## 型錄發行歷史

型錄項目可以宣傳目前發行版本與經核准的歷史發行版本。舊的單版本型錄會維持不變、繼續運作。

```json
{
  "id": "team-setup",
  "version": "1.2.0",
  "download_url": "https://example.com/team-setup-1.2.0.zip",
  "sha256": "<sha256 for 1.2.0>",
  "releases": {
    "1.1.0": {
      "download_url": "https://example.com/team-setup-1.1.0.zip",
      "sha256": "<sha256 for 1.1.0>"
    }
  }
}
```

每個歷史發行版本都需要自己的 `download_url` 與 64 字元的 SHA-256 摘要；與目前發行版本相同，摘要可以使用不區分大小寫的 `sha256:` 前綴與前後空白，其他演算法前綴會被拒絕。發行版本的 `requires`、`provides` 與 `verified` 欄位不會從目前發行版本繼承：請將它們放入該發行版本的記錄中，否則該發行版本將沒有要求、沒有提供數量，並顯示為 `community`。其他共用中繼資料（例如名稱、說明與作者）會被繼承，發行版本記錄可以覆寫它們。發行版本記錄不能包含 `id`、`version` 或 `releases`。

`specify bundle install team-setup --version 1.1.0` 會選取該套件組發行版本、下載該發行版本的成品、驗證其摘要，並檢查其資訊清單是否宣告型錄 ID 且版本與所選發行版本相同。`v1.1.0` 與 `1.1.0` 等等效拼寫視為相符；型錄鍵的拼寫僅供顯示。它永遠不會覆寫 `bundle.yml` 內部的元件釘選。`--version` 僅適用於型錄，因此不能為空、不能與本地路徑併用，也不能與 `--refresh` 組合使用。

系統只會查詢列出該套件組的最高優先級型錄；缺失的版本不會退到較低優先級的型錄。僅供探索的來源仍不可安裝，包括精確的歷史發行版本。型錄中任何位置出現重複的 JSON 鍵，都會在讀取時被拒絕。歷史 `download_url` 值必須使用 HTTPS（或 localhost 上的 HTTP），且發行版本鍵必須是可與 PEP 440 比較的嚴格 SemVer 值。版本鍵必須互不相同，包括 PEP 440 等效拼寫（例如 `1.0.0-rc.1` 與 `1.0.0-rc1`），且不能重複目前版本。`bundle update` 一律選取目前發行版本。官方與社群型錄目前每個套件組只宣傳一個發行版本。

發行歷史會在其型錄來源載入時驗證。格式錯誤的 `releases` 對應，會使 `install`、`info`、`update` 與 `search` 在查詢該來源時失敗。解析會在第一個列出該套件組的來源後停止，因此當較高優先級來源提供該 ID 時，較低優先級來源中被遮蔽的格式錯誤項目仍不會被觀察到；`search` 會載入每個來源，因此被遮蔽的格式錯誤項目仍會導致它失敗。

## 更新套件組

```bash
specify bundle update [<bundle_id>]
```

| 選項           | 說明                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| `--all`          | 更新每個已安裝的套件組                                                                                         |
| `--integration`  | 覆寫重新整理元件時使用的整合；僅在專案的作用中整合無法判定時套用 |
| `--offline`      | 不存取網路                                                                                             |

重新解析套件組，並透過每個基礎建構元素的更新路徑**重新整理**其元件，將已安裝的元件提升到套件組新釘選的版本（或相容的較新封裝修補版本，並發出警告），同時保留基礎建構元素層級的覆寫（例如預設集優先級）。請提供套件組 ID，或使用 `--all` 更新所有已安裝的套件組。

**釘選的型錄發行版本。** 帶有版本釘選的擴充功能、預設集、工作流程與步驟，會從最高優先級的作用中型錄項目選取該精確發行版本。歷史發行版本必須在 `releases` 下宣傳，並帶有自己的成品 URL 與 SHA-256 摘要；打包器永遠不會從目前 URL 猜測舊 URL，也不會退到另一個型錄。未宣傳版本的舊擴充功能與預設集項目是例外：打包器會原樣使用勝出項目，無法強制執行其釘選，也無法驗證已安裝封存檔的版本。請發佈帶版本的項目，讓該釘選可強制執行。基礎建構元素安裝程式會使用所選的工作流程或步驟記錄，不重新讀取型錄，並針對該發行版本驗證下載的封存檔或工作流程／步驟中繼資料。隨 Spec Kit 一起提供且版本相符的釘選工作流程，會使用其隨附副本；版本不同且允許網路存取時，則使用型錄發行版本。沒有釘選的步驟會安裝目前的型錄發行版本。

在沒有明確 `source` 的情況下，隨附的擴充功能與預設集優先於型錄發行版本。即使存在相符的型錄發行版本，驗證仍會拒絕不相容的釘選；相容的較新穩定封裝修補版本則會產生警告。若要選用其精確發行版本，請將勝出的型錄指定為 `source`。

> **每個元件 ID 只能安裝一個版本。** 共用某個元件的套件組必須就其釘選版本達成一致。來自另一個套件組的不同或未知釘選會在安裝前被拒絕，包括在 `bundle update` 期間；重新整理一個套件組無法取代另一個套件組要求的版本。

套件組在同一資訊清單中，每種元件類型只能列出一個元件 ID 一次；同一資訊清單中的重複引用無效，即使其釘選一致。

`provides.<kind>` 引用中可選的 `source`，用來命名預期勝出的元件型錄（如 `specify <kind> catalog list` 所顯示，步驟則為 `specify workflow step catalog list`）。它**不是**成品 URL，也不會覆寫型錄優先級或安裝原則。指定時，即使元件已安裝，也會針對該型錄驗證，而非從 Spec Kit 隨附副本解析；不同的勝出型錄或僅供探索的來源會阻止安裝。若多個作用中型錄共用同名的來源，套件組驗證與安裝會將其拒絕為不明確；請為每個型錄指定唯一名稱。驗證明確來源需要網路存取。基礎建構元素的直接 `--from` URL 是另一條明確要求的獨立路徑。

## 移除套件組

```bash
specify bundle remove <bundle_id>
```

只解除安裝此套件組貢獻的元件，讓另一個已安裝套件組仍需要的任何元件保持原樣（不附帶移除）。若沒有其他套件組擁有保留的元件，其貢獻會轉移到仍要求它的剩餘套件組，以便日後移除該套件組時能將其清除。獨立安裝的元件永遠不會被收編。

## 列出已安裝的套件組

```bash
specify bundle list
```

| 選項   | 說明                  |
| -------- | ---------------------------- |
| `--json` | 輸出機器可讀的 JSON   |

列出專案中已安裝的套件組及其版本、要求的元件數量（包括獨立提供的元件）與安裝時間戳記。搭配 `--json` 時，含有引用的記錄還會包含 `bundle_references`，其中包含每個已解析的直接或遞移引用及其勝出的型錄來源。

## 使用套件組初始化專案

```bash
specify bundle init [<bundle_id>]
```

| 選項           | 說明                              |
| ---------------- | ---------------------------------------- |
| `--integration`  | 整合覆寫                     |
| `--offline`      | 不存取網路                |

確保目前目錄是 Spec Kit 專案（如有需要，以冪等方式初始化），然後視需要安裝指定的套件組。適合作為新檢出的明確單步驟引導。

重複執行 `bundle init` 會跳過套件組已安裝的元件，並保留其本地編輯。它遵循與一般 [`bundle install`](#install-a-bundle) 相同的規則：資訊清單中新增加的元件會被安裝並記錄，但若資訊清單變更了已記錄的套件組版本、變更了自有元件的版本、來源、預設集優先級或策略，或移除了自有元件，它會失敗且不變更已安裝的套件組。若要重新整理元件或套用這類變更，請對型錄套件組使用 `bundle update <id>`，或對本地來源使用 `bundle install <path> --refresh`。

## 驗證套件組

```bash
specify bundle validate
```

| 選項       | 說明                                                          |
| ------------ | ------------------------------------------------------------------- |
| `--path`     | 套件組目錄或 `bundle.yml`（預設：目前目錄）       |
| `--offline`  | 僅針對隨附／已安裝的元件驗證引用          |

回報 `bundle.yml` 是否格式正確，以及每個已宣告的元件引用是否能以其釘選版本解析。對於含有引用的資訊清單，線上驗證會展開完整的引用圖，並檢查展開計畫中的每個元件，包括結構、循環、版本、來源、衝突與安裝原則檢查。引用會針對相符的隨附或已安裝元件檢查，並在線上時針對勝出且允許安裝的型錄中的精確發行版本檢查。明確的 `source` 會針對勝出型錄驗證，而非在本地解析。缺失的發行版本、來源不符、僅供探索的來源，以及格式錯誤的型錄中繼資料都會使驗證失敗；無法離線檢查或因型錄無法連線而無法檢查的元件引用會產生警告。套件組引用擷取失敗（例如套件組型錄無法連線或子資訊清單下載失敗）會使線上驗證失敗，而 `--offline` 則保留逐引用警告。在 `--offline` 模式下，每個已宣告的套件組引用都會產生一則未展開的警告。若在找到相符項目之前，較高優先級的型錄無法連線，查詢仍保持未驗證狀態；較低優先級的相符項目無法定案。驗證不會針對正在執行的 CLI 評估 `requires.speckit_version`；`install` 與 `update` 會強制執行該執行期相容性關卡。與安裝相同，未宣傳版本的舊擴充功能與預設集項目會被接受，不驗證其釘選。

## 建置套件組成品

```bash
specify bundle build
```

| 選項      | 說明                                              |
| ----------- | ------------------------------------------------------- |
| `--path`    | 套件組目錄（預設：目前目錄）           |
| `--output`  | 成品的輸出目錄                       |

從套件組目錄產生單一、具版本、可發佈的 `.zip` 成品。該成品內嵌資訊清單，可以直接使用 `specify bundle install <artifact.zip>` 安裝。

## 發佈套件組

套件組作者在本地驗證並封裝套件組，然後將產生的成品與型錄中繼資料託管在使用者可存取的位置。套件組型錄項目指向該套件組成品，但 `bundle.yml` 內部宣告的元件仍透過隨附元件、已安裝元件，或作用中的擴充功能、預設集、工作流程與步驟型錄解析。

若您的套件組引用了來自非預設型錄的元件，請記錄那些型錄 URL，並在加入那些型錄的乾淨專案中測試安裝路徑。社群套件組提交應在 [Bundle Submission](https://github.com/github/spec-kit/issues/new?template=bundle_submission.yml) 議題中包含該相依性解析證據。

### 提交後會發生什麼

1. 透過 Bundle Submission 表單開啟議題時，GitHub 會套用 `triage-must-have` 判定。套件組提交與擴充功能、預設集提交共用此受理自動化；其他議題的人工分流評分標準維持不變。
2. 維護者在議題分流期間審查該議題，並套用獨立的 `bundle-submission` 標籤，藉此啟動自動化型錄驗證。在此公開儲存庫中，貢獻者無法自行套用該標籤，因此無需標記或重新提出請求：議題只須在分流中等待即可。
3. 自動化工作流程會驗證提交內容，並在驗證通過時，於草稿提取請求中更新 `bundles/catalog.community.json` 與 `docs/community/bundles.md`
4. 維護者審查產生的提取請求，並在核准時將其合併
5. 您的套件組即可透過 `specify bundle search` 探索

## 管理型錄來源

套件組透過具優先順序的型錄來源堆疊探索（專案、使用者與內建範圍）。內建來源如下：

- `builtin://default` — 隨附於 `bundles/catalog.json` 的官方套件組（`bugfix`、`assess` 等），允許安裝。
- `builtin://community` — 位於 `bundles/catalog.community.json` 的社群提交，僅供探索。

每個來源都有安裝原則。`install-allowed` 來源可以從中安裝；`discovery-only` 來源會出現在 `search` 與 `info` 中，但拒絕安裝。在從非預設來源安裝套件組之前，請先檢查作用中的堆疊。

> **請同時審查套件組來源與其元件型錄。** 專案可以在 `.specify/` 下提供自己的套件組型錄，以及允許安裝的元件型錄（擴充功能、預設集、工作流程與步驟）；該專案設定存在，並不表示其中任何內容已經過審查。在從不熟悉的專案安裝套件組之前，請執行 `specify bundle catalog list`，以及它所引入元件對應的 `extension`／`preset`／`workflow catalog list` 與 `specify workflow step catalog list` 命令，並將任何不是您自己新增的來源視為未經審查，直到您已審查為止。

對於工作流程元件，請檢查 shell 的 `run` 與 `env` 欄位及其引用的程式碼，包括作用中覆疊所引入的變更。這也適用於 `strict: true` 步驟：環境繫結可以變更可執行檔查詢或執行期載入。參閱[審查 shell 執行](workflows.md#reviewing-shell-execution)。

### 列出型錄堆疊

```bash
specify bundle catalog list
```

列印作用中、具優先順序的型錄堆疊，以及每個來源的範圍與安裝原則。

### 新增型錄來源

```bash
specify bundle catalog add <url>
```

| 選項        | 說明                                              |
| ------------- | ------------------------------------------------------- |
| `--policy`    | `install-allowed` 或 `discovery-only`                   |
| `--priority`  | 來源優先級（數值越小 = 優先級越高；預設 10） |
| `--id`        | 明確的來源 ID                                      |

註冊專案範圍的型錄來源並將其保存。

以相同的 ID、URL、原則與優先級重新新增同一個來源會成功且不變更設定；不同的設定會被拒絕。

### 移除型錄來源

```bash
specify bundle catalog remove <id_or_url>
```

移除專案範圍的型錄來源。內建的預設來源無法刪除。

> **注意：** `search` 與 `info` 可在任何地方運作：沒有專案時，它們會退回使用內建／使用者型錄堆疊。其餘會變更狀態的命令（`list`、`update`、`remove`、`catalog`）需要已使用 `specify init` 初始化的專案。`install` 與 `init` 在未初始化的目錄中執行時，會視需要初始化專案。
